# Fork ownership map

tmwk is a hard fork of [Orca](https://github.com/stablyai/orca) (the `upstream` remote; `origin` is [tmwkdev/tmwk-app](https://github.com/tmwkdev/tmwk-app), where PRs go). tmwk is responsible for the whole app it ships, including the inherited code it leaves unchanged. Any part of it can be improved where the product needs it. Orca stays an important source of code, fixes and ideas, because its adapters, native chat, remote runtime and mobile app improve daily.

This map records how each area is maintained relative to upstream. It does not record who may change it. Each area has one integration strategy, and the strategy says what we do on the next upstream integration.

**Before editing a path, find its row below.** A path that is not listed is **Follow**. In the notes and logs below, "Own" means code tmwk wrote (Independent); older entries use the former state names.

## Why the map exists

Upstream changes very quickly, and unevenly. Here is a 30-day snapshot taken on 2026-11-17,
with about 7,200 upstream commits in the window:

| Area                                          | Commits | Lines changed |
| --------------------------------------------- | ------: | ------------: |
| `src/main/runtime/orchestration` (~55k lines) |     288 |          115k |
| `src/cli/orchestration`                       |      15 |            7k |
| `skill-guides/orchestration.md`               |      22 |           424 |
| `src/main/native-chat`                        |     541 |          444k |
| `src/renderer/src/components/native-chat`     |     880 |          301k |

The orchestration internals rewrite themselves about twice a month. The `orca` CLI in front of them barely moves. Upstream treats the CLI as a compatibility surface, because skills depend on it and paired servers on different versions talk through it: retired commands return recovery text instead of disappearing.

Changing inherited code adds to the work of reconciling future updates. That cost should shape the implementation, but it does not prevent it. The map keeps the cost visible: every area we diverge from is named, with its reason, so each integration knows what to reconcile and nothing drifts unrecorded.

## Strategies

| Strategy        | Development rule                                                                                                                                                                   | Upstream integration rule                                                                                                                                    |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Follow**      | Reuse the inherited implementation. The first intentional local change updates the map and records the reason in the same PR.                                                      | Integrate upstream normally and check its effect on tmwk.                                                                                                    |
| **Maintain**    | Modify inherited code at its existing path. Changes can include substantive behavior and focused restructuring. Record the intended difference and the dependencies it introduces. | Reconcile both implementations. Review relevant upstream changes even when Git merges them without conflict. Retire local changes when upstream covers them. |
| **Independent** | tmwk determines the design and behavior. This includes code with no upstream counterpart and inherited areas whose design we deliberately take over.                               | Review upstream changes affecting the area and its dependencies; port useful changes explicitly. Record what was ported, declined or deferred.               |

Unlisted inherited paths default to Follow. A developer moves an area to Maintain in the same focused PR as its first change; no separate approval is needed to edit an upstream path. Independent is a deliberate design choice with a stated scope and reason, not an automatic result of a difficult merge.

Replacement and retirement are transitions, not additional strategies. An unused implementation may stay while removal would disrupt callers or compatibility, and may be removed once those dependencies are handled.

The former states migrated as: Track to Follow, Extend to Maintain, Adopted to Independent, Own to Independent. The migration changed maintenance policy only. No code moved or was renamed. New code belongs in the module that owns its behavior; `tmwk` directories remain for tmwk concepts and are not mandatory destinations.

## Orchestration and the work layer

tmwk's work layer is the main chat, tickets and their owners, reports, questions and decisions, briefs and preferences, worker instructions and tmwk's worker skill, the away digest and acceptance. It is built on Orca's agent primitives: agent launch, messaging, session reads and host placement.

Orca's orchestration has a work model of its own: Runs, Tasks, gates, the coordinator. tmwk's ticket model replaces it by no longer depending on it. It stays in the tree, integrates like any Follow code, and still serves agents that use the `orchestration` skill directly. tmwk ships its own `tmwk` skill beside it for owners of tmwk tickets, and points to `orchestration` for Orca's commands. The history is in [orchestration-ownership-plan.md](orchestration-ownership-plan.md).

Boundaries follow actual responsibilities:

- **Across hosts or processes:** preserve RPC, IPC, CLI and wire contracts, including capability checks and behavior with older supported peers.
- **Within a process:** use typed service interfaces and the existing dependency direction. Calling a local service is valid; routing every local call through RPC is not a requirement.
- **Across lifecycle or storage owners:** use the operation that owns the mutation, cleanup, authorization and event publication. A direct database or private-state shortcut is not a substitute.

## Identity and egress

A boundary cuts across every strategy: **who the app is and where it talks**. This covers the bundle id, `appName` and the Keychain name, data folders, the command name, the URL scheme, launchd labels, the update and release repos, and every outbound host, endpoint and key. These values are tmwk's even inside Follow code.

**Rule:** a value that names the app, its folders, command or scheme, or a remote host, repo or key, is read from `src/shared/tmwk/identity/` (Independent). No Follow or Maintain file holds it as a literal. Inherited code reads it through one-line Maintain patches, preferably at an upstream chokepoint. `pnpm tmwk:identity-tripwire` reports new upstream references on every integration and every night, and each night with hits opens a tmwk ticket. Display text and brand assets stay in `src/shared/tmwk/branding/`. The plan, the inventory and the build order are in [identity-egress-guide.md](identity-egress-guide.md) (planned: rows below marked _planned_ land with its steps I0–I5).

## Changing a path's strategy

Moving a path to a new strategy is a decision, so record it rather than letting it drift:

1. Update the row above.
2. Add a line to the [decision log](#decision-log) with the date and the reason.
3. Moving to **Maintain**: add a line to the [Maintain patch log](#maintain-patch-log) with the intended difference and the dependencies it introduces.
4. Moving to **Independent**: state the scope and the reason, and add the area to the integration review list.

Signals that a path should move:

- A Maintain path conflicts on most integrations. Upstream is reshaping it, so the local change should go upstream, be retired, or the area becomes Independent.
- A Follow path needs a local fix. Make it at the path that owns the behavior, and move the path to Maintain in the same PR.
- tmwk needs product behavior that differs in purpose or lifecycle from the inherited code. Build it where it belongs and mark the area Independent.

## Syncing with upstream

Integrated upstream baseline: `f1e1f44779fa` (fork point; no upstream integration yet).

Every Maintain and Independent area records its last reviewed upstream commit. No integration has happened, so for every area it is the baseline `f1e1f44779fa`. A row gets its own commit once an integration reviews it, and a note on that row says so. A planned nightly upstream watch will list the areas upstream touched since their last review (not built yet).

Integrate weekly, and earlier for an important fix. A fetched commit or a partly reviewed candidate does not become the baseline.

1. `git fetch upstream`. Pick a candidate commit and pin it. Pushing to `upstream` is disabled.
2. Open an integration branch from `origin/main` and merge the pinned commit. Record the previous baseline, the candidate commit and the tmwk base, and summarize upstream changes by subsystem, noting overlap with Maintain areas.
3. **Follow:** should merge clean. Check the effect on tmwk. A conflict means an unrecorded local edit: record it as Maintain, or revert it.
4. **Maintain:** reconcile both implementations even when Git merges cleanly, because a clean merge is evidence about text, not product behavior. Review changes to callers, types, storage, events and protocols around each patch. For each local change, keep it, adapt it or retire it, and explain what remains. Reapply patches from the [patch log](#maintain-patch-log) where a conflict removed them.
5. **Independent:** never use a blanket merge option that prefers all local files. Review upstream's diff of the area and its dependencies. Record each change as ported, declined or deferred, with the reason.
6. **Upstream's `orchestration` skill:** read `git diff <previous baseline>..<candidate> -- skills/orchestration skill-stubs/orchestration.md skill-guides/orchestration.md skill-guides/orchestration`. Fix the tmwk skill or preamble in the PR if a change contradicts them.
7. **Generated:** take theirs, then run `pnpm generate:bundled-skill-guides`, `pnpm generate:skill-bundle-manifest`, `pnpm generate:rpc-params-catalog` and `pnpm sync:localization-runtime-catalog`.
8. **Identity and egress:** run `pnpm tmwk:identity-tripwire --diff origin/main` (_planned_, identity guide I2). Clear every hit in the PR: route it through `src/shared/tmwk/identity/`, accept it with a reason, or accept it as `later: <ticket>` and open that ticket. List the hits and what was done in the PR description. Needs the `upstream` remote: `git remote add upstream https://github.com/stablyai/orca.git` and `git remote set-url --push upstream DISABLED`.
9. Run `pnpm check:changed`, then the main chat smoke check (end-to-end delegation, defined in [main-chat.md](main-chat.md#milestones)).
10. Full validation is the nightly on the MBP (about 2 hours; there is no GitHub Actions). Fix integration regressions on the candidate branch and record deferred work with its reason. The integrated baseline above advances only when the candidate lands. A failed candidate leaves it unchanged.
11. Note any Maintain path that conflicted. Repeated conflicts mean the path should be simplified, retired or made Independent.
