# Brand plan: the app is tmwk, not Orca

The goal: someone who opens the app, reads its menus, or follows its prompts should not think it is still vanilla Orca. The owner set the floor on 2026-11-19: "We can't have the name orca all over though at the very least." The theme and every other visual stay as they are. This plan finds every place a person sees the name. It separates the user-visible name from internal identifiers. It picks the seams that rename the most for the least upstream sync cost, and it gives an order.

Written on 2026-11-19 from a read of `origin/main` at `749425683b` (PR #25 merged; O0 and O1 of the [orchestration ownership plan](orchestration-ownership-plan.md) not yet built). No gate was run and nothing was launched. Every code reference below was found by reading the code. Counts come from `grep` over the tree and exclude `*.test.*` unless noted. Commit counts are from `git log --since=2026-10-20 origin/main -- <path>`, which includes upstream merges. Items marked **(verify)** were not run and must be checked before anything relies on them.

Updated on 2026-11-19 with the owner's answers (see [Owner answers](#owner-answers)). The answers add a brand-asset step (B7) and make side-by-side install with Orca a requirement (see [Side by side with Orca](#side-by-side-with-orca)). The brand assets were read from `tmwkdev/grenada` at `10d408f`, `apps/desktop/assets/brand`, with `gh api`, read-only.

**Done when:**

- The desktop app's window title, app menu, About panel, dock name and tray say tmwk. So do the menus, dialogs, settings, onboarding, empty states and notifications that go through the translator, in every built-in locale.
- No identifier that existing installs, paired servers, the mobile app or agents depend on has changed: package name, `ORCA_*` env vars, IPC/RPC names, userData paths, bundle ids, `orca://`, and the `orca`/`orca-dev` commands.
- The rename costs at most a handful of one-line Extend patches in low-churn files, plus Own files. No locale catalog or upstream string is edited in place.
- The license notice is kept, and upstream is credited as the base.
- The dock, window, favicon and the main view's empty screen use tmwk's beaver assets, not Orca's.

## The findings in short

1. **There is no product-name constant.** Upstream writes "Orca" inline: 22,398 lines in `src/` contain the word `Orca` (case-sensitive, non-test), and 71,538 lines contain `orca` in any case. Even the app name is a local constant, `BASE_APP_NAME = 'Orca'` in `src/main/startup/profile-startup/dev-instance-identity.ts:5`, and `productName: 'Orca'` sits in `config/electron-builder.config.cjs:264`. A find-and-replace would touch about 8,800 files and conflict on every sync.
2. **But nearly every string a user reads passes through one function.** Renderer and main both build their translator with `createOrcaI18n` in `src/shared/i18n/orca-i18n-instance.ts`. Its `translate(key, fallback)` returns the English fallback written inline at the call site, or the catalog value in other locales. It already post-processes every result (pseudo-localization, line 103). That file had **1 commit in 30 days**. A one-line brand pass there renames the 1,407 English and about 1,250–1,370 per-locale catalog strings that contain "Orca", plus every inline English fallback, in all 11 locales, with no catalog edit. The catalogs themselves are the worst place to edit: `en.json` had 726 commits in 30 days. See [The translation seam](#the-translation-seam).
3. **The app name splits into a display name and a Keychain name, and only the display name may change.** `getDevInstanceIdentity` returns `name` (dock title, app menu label) and `appName` (`app.setName`, which fixes the macOS safeStorage Keychain service). The code's own comment: "packaged forks must retain their CFBundleName-derived encryption keys" (`dev-instance-identity.ts:15`). Changing `appName` would leave every secret encrypted under the old Keychain name unreadable. Changing `name` is safe.
4. **What people see today is the dev build, and it says "Orca" in five places that the translator does not reach.** These are: the dock and `.app` bundle name `Orca: <branch>` (`config/scripts/development/launch/run-electron-vite-dev.mjs:121`), the app menu label (`identity.name`), the About panel (`app.name` in `src/main/startup/gpu-recovery/gpu-lifecycle.ts:45`), the window `<title>Orca</title>` (`src/renderer/index.html:9`) and its fallback (`src/main/window/createMainWindow.ts:136`). There is no packaged tmwk release: `gh release list -R tmwkdev/tmwk-app` is empty, and the coordinator CLI is `orca-dev`.
5. **"tmwk" appears nowhere in the UI today.** The main chat's sidebar entry is "Chat" (`tmwk.mainChat.title`), and no string names the product. Removing "Orca" alone leaves the app unnamed. The seam has to put "tmwk" in.
6. **Some "Orca" text is honest and must stay.** Links to orca.dev docs, the changelog, Discord, and the GitHub star card (`StarNagCard`: "Orca is open source. If it helped today, a GitHub star helps…") point at upstream's sites. Renaming their labels to tmwk would mislead. 53 English catalog strings mention Orca next to docs, Discord, GitHub, community or a changelog. The brand pass needs an exclusion list. The owner chose to relabel the star prompt so it points at tmwk, and to hide the Discord and community links (D47).
7. **Packaged distribution is a separate, larger project.** A packaged tmwk with today's config would be `Orca.app`, `com.stablyai.orca`, userData `orca`, `/usr/local/bin/orca` and `orca://`. Its auto-updater would pull **upstream's** releases (`publish.owner: 'stablyai'`, `config/electron-builder.config.cjs:826`). It would collide with a vanilla Orca install on the same machine. The owner wants an installable tmwk that lives beside Orca (D53). [Side by side with Orca](#side-by-side-with-orca) lists each collision; building it is a separate plan.

## The translation seam

`createOrcaI18n` (`src/shared/i18n/orca-i18n-instance.ts`) is the single place where renderer and main turn a key and an English fallback into text:

```ts
const value = i18n.t(key, { defaultValue, ...rest })
return isPseudoLocalizationLocale(i18n.language) ? pseudoLocalizeString(value) : value
```

The patch is one wrapped value: `const value = brandTmwkText(key, i18n.t(key, { defaultValue, ...rest }))`. `brandTmwkText` lives in an Own file, `src/shared/tmwk/branding/tmwk-brand-text.ts`:

- It replaces `\bOrca\b` (case-sensitive, whole word) with `TMWK_PRODUCT_NAME`. "Orca's" becomes "tmwk's", and "Orca server" becomes "tmwk server". Lowercase `orca` is untouched, so `orca tmwk brief`, `~/.config/orca` and `orca://` in copy stay correct.
- It keeps `ORCA` (uppercase, as in `ORCA_*` env names; 21–27 occurrences per CJK/ru catalog) and words that merely contain it.
- It skips keys on an exclusion list, `TMWK_BRAND_KEEP_KEYS`, for strings that name upstream's sites or community (D47).
- The Korean catalog has one transliteration, `오르카` (`ko.json:3469`, in a terminal-reconnect message), which the pass does not catch. It is left alone.

What it reaches: every renderer `t()`/`translate()` call (`src/renderer/src/i18n/i18n.ts:123-125`, and `use-translate.ts:24` delegates to it), every `translateMain` call (`src/main/i18n/main-i18n.ts:41`): menus, tray, native dialogs, pop-out and Space window titles. Plugin language packs load into the same instance, so they are covered too. The renderer's plain-translation cache (`i18n.ts:87`) sits above `translate`, so it caches branded text.

What it does not reach: identity strings (dock, app menu, About), `index.html`, untranslated literals, the CLI, skills, mobile and remote content. Those are D45–D50.

Why not the alternatives:

- Editing the catalogs: 726 commits/30d on `en.json`, 167 on `en-runtime-required.json`, and English mostly isn't in a catalog at all (inline fallbacks).
- A tmwk "language pack" plugin: packs add a locale, not an English override, and the user would have to pick it. **Verified on 2026-11-19:** `replacePluginLanguagePackResources` registers each pack under its own `resourceLanguage`, and `resolveResourceLanguage` reaches a pack only for a `plugin:` locale the user selected.
- An i18next `postProcess` module: the same effect, but it registers in two init sites (`i18n.ts:71`, `main-i18n.ts:35`) instead of one, and pseudo-localization already shows the house pattern.

- New upstream strings that say "Orca" are branded automatically if they go through the translator, which upstream's localization gate enforces for renderer copy.
- On each sync, review new upstream strings that mention docs, Discord or GitHub and add them to `TMWK_BRAND_KEEP_KEYS` if needed. `git diff <last-sync-base>..upstream/main -- src/renderer/src/i18n/locales/en.json | grep '^+.*Orca'` lists them.
- If upstream ever adds a product-name constant, move the seams onto it and drop the patches.

## First-class citizens

- **Cross-platform:** the translation seam is platform-neutral. The dock title is mac-only. On Windows and Linux the dev title comes from the same `identity.name`, and the window title from `index.html`. Nothing touches `AppUserModelId`, the Linux `StartupWMClass` or install paths.
- **Remote hosts:** a remote `orcad` host runs the same `createOrcaI18n` for main-process text it sends (for example runtime errors via `translateMain`), so branded text depends on the host's version. A host on an older build still says Orca until it updates. Nothing in the RPC contract changes.
- **Mobile:** unchanged and still Orca-branded (D52). Pairing keeps working because `orca://` and the relay are untouched.
- **Folder workspaces:** not affected.

## Risks

- **A keep-list miss.** A label pointing at orca.dev could read "tmwk docs". Mitigation: B1 reads all 53 candidates, and each sync greps new ones.
- **Text that should say Orca reads as tmwk.** "Install Orca on this server" (`agentLaunch.updateServer`: "Update Orca on this workspace's server") would read "Update tmwk", which is correct when the server runs tmwk's build and misleading when it runs upstream's. tmwk's hosts run tmwk's build today **(verify on the MBP host)**.
- **The CLI and the UI disagree.** The UI says tmwk and the command is `orca`. Mitigation: tmwk copy writes "the tmwk CLI (`orca`)"; D48 keeps the alias option open.
- **Interpolated values are branded too.** The pass runs on the finished string, so a value inserted into a translated message, such as a project named `Orca`, would read `tmwk`. Branding the template before interpolation would mean a second patch inside i18next. Accepted for v1.
- **A Keychain regression.** If a later change touches `appName`, stored secrets break. Mitigation: B2's acceptance checks a signed-in account; the plan states that `appName` stays.
- **Direct react-i18next callers.** The 38 sites that bypass `translate` could render unbranded text if any uses `t` directly (`space.tsx:30` does). **Verified on 2026-11-19 (B1):** 37 of the 38 calls only read `i18n` or subscribe to language changes. `space.tsx:30` uses `t` for two strings (`workspaceSpace.window.errorTitle`, `errorDescription`) that do not mention Orca. The 45 `<Trans>` components all take `defaults` that came from `translate`, and none passes `i18nKey`, so their text is already branded.
- **Release workflows on the fork.** Most are guarded by `github.repository == 'stablyai/orca'`. `mobile-ios-release.yml` and `mobile-android-release.yml` are not, and trigger on `push`. They should fail for lack of secrets **(verify their trigger filters)**. Not caused by this plan; noted because a tmwk tag push could start them.

## Public release channel

The owner will host downloads on GitHub (second round, item 4). This is what that looks like, from how upstream's updater and release flow work today.

### What the app reads

- **Stable updates.** The packaged app does not use the builder's `publish` block at runtime. `updater-setup.ts:172-175` sets electron-updater to the `generic` provider at `https://github.com/stablyai/orca/releases/latest/download`. So the app downloads `latest-mac.yml` (macOS), `latest.yml` (Windows) or `latest-linux.yml` (Linux) from the repository's **latest** release, then the zip, installer or AppImage it names. macOS updates come from the `zip` target, which the config already builds beside the `dmg` (`electron-builder.config.cjs`, `mac.target`), with a `.blockmap` for delta downloads.
- **Release candidates.** `rc` builds are GitHub prereleases in the same repository. The app finds them through the repository's Atom feed (`updater-prerelease-feed.ts:15`, `https://github.com/stablyai/orca/releases.atom`) and pins the tag (`updater-release-feed.ts:121`), because `latest/download` never points at a prerelease.
- **Dev channels.** `hourly`, `daily` and `adhoc` builds go to separate repositories (`src/shared/updater/release-channel.ts:22-24`), because GitHub's Atom feed lists only the 10 newest releases and hourly tags would push stable and RC out of it. Each is listed through the GitHub API (`updater-release-builds.ts:26`).
- **Readiness.** Before offering an update, the app checks that every asset of the release exists (`updater-release-readiness.ts:4`), which is why upstream publishes as a draft and then promotes the release (`releaseType: 'draft'`, `electron-builder.config.cjs:831`).

**Until this changes, a packaged tmwk build would look for updates on Orca's releases**, in five places: the builder's `publish` (`owner: 'stablyai'`, `repo: 'orca'`) and the four runtime files above. P5 points all of them at tmwk's repositories through one Own constant.

### Where the downloads live

**Decided (owner, 2026-11-19): "Let's make the repo public."** `tmwkdev/tmwk-app` is public now (`gh repo view` reports `PUBLIC`). Releases and updates come from `tmwkdev/tmwk-app` itself, with no separate releases repository. One repository holds the code, releases, stars and issues, the same layout as upstream. GitHub serves release assets anonymously only from public repositories, and electron-updater's `generic` provider sends no token, so this is what makes downloads and updates work without a token.

The download page is `https://github.com/tmwkdev/tmwk-app/releases/latest`, and the asset names come from the overlay config (`tmwk-macos-arm64.dmg`, `tmwk-macos-x64.dmg`, `tmwk-windows-setup.exe`, `tmwk-linux.AppImage`).

### Channels for tmwk

- **Stable**: normal releases in the public repository. Every install follows it by default.
- **RC (prerelease)**: GitHub prereleases in the same repository, for the owner to try a build before promoting it. Same updater path as upstream.
- **Dev channels**: not needed at first. tmwk's dev loop is running from source (`orca-dev`). Add a separate `tmwk-dev` releases repository only if nightly installable builds become useful, for the same 10-entry feed reason as upstream.

### The release flow

1. Bump `version` (tmwk's own version line, separate from upstream's `1.4.x`, **(verify that the updater's version comparison accepts it)**) and tag `vX.Y.Z` on `main`.
2. CI on macOS builds with the overlay config: `electron-builder --config config/tmwk/electron-builder.tmwk.cjs --mac --publish always -c.publish.releaseType=draft`.
3. **macOS signing.** electron-builder signs with the Developer ID Application certificate from `CSC_LINK` and `CSC_KEY_PASSWORD`, with the hardened runtime and `resources/build/entitlements.mac.plist`. It then notarizes through Apple's notary service with `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID` (or an App Store Connect API key), and staples the ticket. Upstream ties both to release builds (`hardenedRuntime: isMacRelease`, `notarize: isMacRelease`). The overlay sets tmwk's team id in place of `ORCA_MAC_TEAM_ID`. Squirrel.Mac installs only signed updates, so **macOS auto-update works only once signing is in place**. Until then, macOS builds are manual downloads that Gatekeeper warns about.
4. **Windows** builds ship unsigned (owner decision). The overlay must not set `win.signtoolOptions.publisherName`: electron-updater checks the installer's Authenticode publisher when one is configured, and an unsigned installer would fail that check **(verify how `NsisUpdater` behaves with no `publisherName`)**. SmartScreen warns users on first run. Never disable `verifyUpdateCodeSignature` (`updater-setup.ts:170`).
5. Linux AppImage and deb need no signing.
6. Check the draft release has every asset (`latest*.yml`, zips, blockmaps, dmg, exe, AppImage), then publish it. The `latest/download` URL moves to it, and installs update on their next check.

The workflows are tmwk's own (`.github/workflows/tmwk-release-*.yml`, Own). Upstream's release workflows stay Track and stay guarded to `stablyai/orca`.
