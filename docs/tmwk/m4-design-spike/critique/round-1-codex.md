# Round 1 — Codex critique

B is the strongest starting point. D supplies the missing depth. C is worth a second experiment because it gives Chat the right prominence, but its thread metaphor needs correction. Most of this set still asks me to monitor execution rather than direct outcomes.

The three highest-impact fixes: preserve decision → stop → result priority; show the reason before execution metadata; make sessions an explicit disclosure beneath a ticket. Simplicity means fewer routine judgments, not merely fewer rows.

## Direction verdicts

- **A — Cut as a default.** Correct ownership hierarchy, separate agent/status indicators, useful session roles. But the eight-ticket sample already pushes ongoing work below the dock. Model strings and repeated owner states consume more space than outcomes; the actual question truncates. This is Orca's management burden wearing ticket names. Keep its expanded subtree as an inspection state.
- **B — Finalist.** Best attention allocation: the question, outage, and PR are readable; quiet work remains visible; accepted work recedes. However, each attention item spends three lines on category/title/reason, while quiet rows spend scarce space on provider logos. Remove the separate category line where the reason explains it, add project disambiguation when necessary, and provide session disclosure. Quiet must not mean inaccessible.
- **C — Finalist, substantially revised.** The clearest commitment to one conversation, with excellent breathing room. But tickets visually become chat threads, suggesting several interchangeable conversations. No attention heading explains the ordered list, and no session affordance preserves M4's depth. Keep Chat prominent; label the ticket section independently and add disclosure. Collapsed Projects is a good escape hatch.
- **D — Finalist as B's denser sibling.** All eight tickets fit and only the selected subtree expands. This is the best demonstration of accessible power. But session count, changed dot, time, and state turn rows into instrument panels while hiding the actual decision and blocker. Give attention rows B's reason line; remove routine counts and ages; collapse accepted work. Selection and expansion must be separate actions.
- **E — Cut.** Familiar project context and host placement are useful during inspection. As the default, it buries the stopped website ticket beneath healthy tmwk-app work. Project counts are also ambiguous: tmwk-app says two while showing five tickets. It preserves today's organizing habit instead of the intended attention model. Offer project filtering, not project-first triage.
- **F — Cut as navigation; retain its summaries.** “Watching 3 PRs · fixed 2 failures today” communicates delegated value better than a spinner. But changed is not needs-you: reading a decision must never demote an unresolved decision into “Everything else.” The count strip repeats information and gives quiet states equal visual weight. Use change markers and handled summaries inside B or the away message.
- **G — Cut.** The detail panel explains the selected ticket and placement clearly. The rail makes every other ticket a memorization test: Ns, Rn, Ff are not destinations I can scan. More work makes this worse. It also sacrifices the overview to show one ticket's machinery. Reuse the detail content after opening a named ticket.
- **H — Cut as the M4 replacement.** Cards finally have room for useful progress and next-check text. But an entire navigation step hides quiet work whenever Chat is open; a four-column board spends a full column on one accepted item. Provider-logo clusters explain little. Keep a full overview as an optional expansion, preferably a list; H alone does not meet the ticket sidebar milestone.

## Next round

Advance **B+D** as the recommended default: reasons for attention, compact quiet rows, sessions disclosed on demand. Compare it with **revised C**: prominent Chat, a separately named ticket list, the same attention ordering and expandable sessions. These are two coherent alternatives; do not manufacture a third finalist from rejected chrome.

## Shared failures and required states

The glyph vocabulary is legitimate, but red/green dots alone carry too much meaning. Keep icons and concise reasons; distinguish result awaiting acceptance from accepted. Ongoing is a ticket kind, not an exclusive execution state: monitoring work can run, stop, or need a decision. Do not make those lanes contradictory.

Unlabeled ages could mean last activity, time waiting, or stale data. A disconnected host needs last-known state and an observed timestamp; “unreachable” does not prove its environment stopped. Placement belongs inside the ticket except when it explains a problem. Project names matter for duplicate titles, while folder workspaces must remain reachable without a fabricated repository.

Both themes are quiet, but muted reasons deserve more reading priority than logos and timestamps. “Done today” prematurely hides older history; “Fix flaky checks detail link” reads like leaked implementation copy. Retain “Chat”; never restore the retired labels.

Show 20 tickets, long titles, no attention items, zero tickets, and disconnected data. Keep outstanding needs pinned regardless of read status, preserve the current row during updates, and provide searchable ticket access. Empty work should offer delegation through Chat. Demonstrate keyboard ticket opening, session expansion, return to Chat, and decision/result review in one or two actions; static PNGs establish none of those behaviors.

## Missing experiment

Try a **persistent work shelf beside the conversation**: named compact tickets remain stable, while a separate attention queue contains the actual pending question, recovery, or result. Resolving attention never relocates the ticket. This separates navigation from triage and tests simplicity without hiding quiet work or turning tickets into chat threads.
